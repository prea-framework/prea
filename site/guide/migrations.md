# Migrations

A migration is a SQL file that changes the database: it creates a table, adds a column, fills in data. Migrations run in order, each one once, so every database you have (yours, your colleague's, production) goes through the same changes.

::: info What you'll learn
- What a migration file looks like
- How Preá writes migrations from your models
- How migrations run: at startup or with `prea migrate`
- What a safe setup for production looks like
:::

## A migration file

```
migrations/
├── 0.0.1_create_task_table.sql   written by Preá from the models
├── 0.0.2_add_due_date.sql        written by you
└── 0.1.0_backfill.sql            versions may skip numbers
```

```sql
alter table task add column due_date date;

-- prea:down
alter table task drop column due_date;
```

- **The name** is `<version>_<name>.sql`. Versions are semantic (`0.0.1`) by default, or timestamps (`20261013120000`) with `database.migrations.version: timestamp`. Don't mix the two in one folder.
- **The SQL runs exactly as written**, including functions with `$$` bodies.
- **`-- prea:down`** is optional. Below it goes the SQL that undoes the migration. Without it, `prea migrate down` refuses to undo that migration, rather than undoing half of it.
- **`-- prea:no-transaction`**, on the first line, runs the file outside a transaction, which `create index concurrently` needs. Otherwise each migration runs in a transaction: if it fails, none of it stays, and the next ones don't run.

## Written from your models

In the `dev` profile of a new project, two settings are on:

```yaml
# config/application-dev.yaml
database:
  migrations:
    from_models: true   # a model change becomes a migration at startup...
    on_start: true      # ...that is applied right away
```

Change a model, save, and `prea dev` restarts. Preá compares your models with the database and writes the difference as a new migration:

```sql
-- migrations/0.0.2_alter_task_table.sql
-- Generated by prea from the models: review it before committing.

alter table "task" add column "due_date" timestamptz;

-- prea:down
alter table "task" drop column "due_date";
```

It finds missing tables, columns and indexes, and changes of type or nullability. **Review every generated file before you commit it.** It is a starting point, and you own it from then on.

The file is named after what it does: `create_task_table`, `alter_task_table`, or `create_list_table_and_alter_task_table` when one start changes several tables.

::: details Why isn't a removed field dropped?
A column that exists in the database but not in the model appears in the migration **commented out**. Dropping a column destroys its data, so that decision is yours: uncomment the line if you mean it.
:::

When there are pending migrations, Preá doesn't generate anything: they might already contain the change. Apply them first.

## Write one yourself

For changes a model can't express, like moving data or creating a view, create an empty migration and write the SQL:

```bash
prea migrate create backfill_titles
```

```
created migrations/0.0.3_backfill_titles.sql
```

## The CLI

| Command | What it does |
|---|---|
| `prea migrate up` | applies every pending migration |
| `prea migrate up 0.0.2` | applies the pending ones up to that version |
| `prea migrate down` | undoes the last applied migration (`down 3`: the last three) |
| `prea migrate status` | lists each migration as applied, with the date, or pending |
| `prea migrate validate` | checks the files without running them, for CI |
| `prea migrate create <name>` | creates the next empty migration |

Pass a profile before the command: `prea migrate --profile prod status`.

```
0.0.1_create_task_table                  applied 2026-10-15 11:59:10
0.0.2_add_due_date                       pending
```

`prea migrate` builds your app and runs it in a special mode: instead of serving, the app runs the command with its own configuration and database. You never repeat the connection settings for the CLI, and a migration never needs the app's other secrets.

## At startup

When the app starts, the database steps run in this order:

1. **`from_models`** writes a migration with the difference.
2. **`on_start`** applies the pending migrations.
3. **`schema`** checks or changes the tables, as [Models & schema](./models#the-schema-setting) describes.

Preá keeps track of the applied migrations in the `prea_migrations` table. An advisory lock keeps two instances from migrating at the same time, so starting several copies of the app at once is safe. A pending migration with an older version than the last applied one, which happens after merging two branches, runs too.

## In production

```yaml
# config/application-prod.yaml
database:
  schema: validate          # the tables must match the models, or the app won't start
  migrations:
    from_models: false      # never write files in production
    on_start: true          # or false, and run prea migrate up in your deploy
```

Apply migrations either at startup (`on_start: true`) or as a deploy step (`prea migrate up`), and keep `schema: validate` so an app never runs against tables it doesn't expect.

`from_models` can't be combined with `schema: update`, `create` or `create-drop`, because one would apply directly what the other records. The app stops and says so.
